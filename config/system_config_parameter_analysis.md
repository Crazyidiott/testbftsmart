# BFT-SMaRt system.config 参数分析

> 目标：识别每个参数的用途、是否属于本地可调参数（不需要共识）或需要共识的参数、是否适合动态调参、以及推荐的调参频率。

## 术语说明

| 类别 | 含义 |
|------|------|
| **本地可调** | 每个节点可以独立调整，不需要所有节点保持一致值 |
| **需要共识** | 所有节点必须使用相同的值，修改需要通过共识协议同步 |
| **半共识** | 理论上各节点可以不同，但不一致会导致性能退化或协议异常，建议通过共识同步 |

## 已有动态调参参数（当前实现）

你的项目中 `RLAgentConnector` 已经支持通过 `setDynamicConsensusConfig()` 动态调整以下两个参数，它们通过 `volatile` 字段实现热更新：

| 参数 | 当前状态 |
|------|----------|
| `system.totalordermulticast.maxbatchsize` | ✅ 已实现动态调参 |
| `system.totalordermulticast.batchtimeout` | ✅ 已实现动态调参 |

## 一、通信配置（Communication Configurations）

### 1. `system.communication.secretKeyAlgorithm`
- **当前值**: `PBKDF2WithHmacSHA1`
- **用途**: 生成MAC密钥的算法
- **类别**: 🔴 需要共识 — 所有节点必须使用相同的密钥算法才能互相验证MAC
- **适合动态调参**: ❌ 不适合。更换密钥算法涉及密钥重新协商，运行时切换会导致通信中断
- **建议**: 静态配置，部署前确定

### 2. `system.communication.secretKeyAlgorithmProvider`
- **当前值**: `SunJCE`
- **用途**: 密钥算法的Java安全提供者
- **类别**: 🟡 本地可调（理论上不同节点可用不同Provider，只要算法兼容）
- **适合动态调参**: ❌ 不适合。Provider变更需要重新加载安全模块
- **建议**: 静态配置

### 3. `system.communication.hashAlgorithm`
- **当前值**: `SHA-256`
- **用途**: 哈希计算算法（用于消息摘要）
- **类别**: 🔴 需要共识 — 所有节点必须使用相同的哈希算法来验证消息
- **适合动态调参**: ❌ 不适合
- **建议**: 静态配置

### 4. `system.communication.hashAlgorithmProvider`
- **当前值**: `SUN`
- **用途**: 哈希算法的Java安全提供者
- **类别**: 🟡 本地可调
- **适合动态调参**: ❌ 不适合
- **建议**: 静态配置

### 5. `system.communication.signatureAlgorithm`
- **当前值**: `SHA256withECDSA`
- **用途**: 签名算法（用于验证客户端请求和副本间消息）
- **类别**: 🔴 需要共识 — 所有节点和客户端必须使用相同的签名算法
- **适合动态调参**: ❌ 不适合。涉及密钥对和证书
- **建议**: 静态配置

### 6. `system.communication.signatureAlgorithmProvider`
- **当前值**: `BC` (Bouncy Castle)
- **用途**: 签名算法的Java安全提供者
- **类别**: 🟡 本地可调
- **适合动态调参**: ❌ 不适合
- **建议**: 静态配置

### 7. `system.communication.defaultKeyLoader`
- **当前值**: `ECDSA`
- **用途**: 默认密钥加载器类型
- **类别**: 🔴 需要共识 — 需要与签名算法和密钥文件匹配
- **适合动态调参**: ❌ 不适合
- **建议**: 静态配置

### 8. `system.communication.useSenderThread`
- **当前值**: `true`
- **用途**: 是否使用独立线程发送数据（异步发送）
- **类别**: 🟢 本地可调 — 纯本地线程模型选择，不影响协议语义
- **适合动态调参**: ⚠️ 理论上可调，但运行时切换线程模型风险较高
- **建议**: 静态配置。如有需要可做为实验参数在启动时调整

### 9. `system.communication.defaultkeys`
- **当前值**: `true`
- **用途**: 强制所有节点使用相同的公钥/私钥对（仅用于实验/测试）
- **类别**: 🔴 需要共识 — 所有节点必须统一
- **适合动态调参**: ❌ 不适合
- **建议**: 静态配置，生产环境应设为false

### 10. `system.communication.bindaddress`
- **当前值**: `auto`
- **用途**: 副本绑定的IP地址
- **类别**: 🟢 本地可调 — 每个节点有自己的绑定地址
- **适合动态调参**: ❌ 不适合。地址绑定在网络层初始化时确定
- **建议**: 静态配置

## 二、复制算法配置（Replication Algorithm Configurations）

### 11. `system.servers.num`
- **当前值**: `4`
- **用途**: 集群中服务器总数 (n)
- **类别**: 🔴 需要共识 — 这是BFT协议的核心参数，决定quorum大小
- **适合动态调参**: ❌ 不适合运行时动态调参。只能通过reconfiguration协议增减节点
- **建议**: 通过BFT-SMaRt自带的reconfiguration机制变更

### 12. `system.servers.f`
- **当前值**: `1`
- **用途**: 最大容忍的拜占庭故障节点数
- **类别**: 🔴 需要共识 — 直接决定安全阈值和quorum计算 (n ≥ 3f+1)
- **适合动态调参**: ❌ 不适合
- **建议**: 与 `system.servers.num` 联动，静态配置

### 13. ⭐ `system.totalordermulticast.timeout`
- **当前值**: `2000` (ms)
- **用途**: 请求超时时间。如果在此时间内共识没有完成，由 `RequestsTimer` 触发 `triggerTimeout`，进而发起 **view change**（领导者切换）
- **类别**: 🟡 半共识 — 各节点可以有不同的超时值，但如果差异过大：
  - 超时过短的节点会频繁发起不必要的view change
  - 超时过长的节点在leader真正故障时恢复缓慢
  - **建议所有节点保持一致或仅有微小差异**
- **适合动态调参**: ✅ **非常适合** — 这是动态调参最有价值的共识参数之一
  - 网络延迟高时增大timeout → 避免不必要的view change
  - 网络状况好时减小timeout → 更快发现故障leader
  - 负载变化时调整 → 高负载下适当增加以避免假超时
- **调参频率**: 中频，建议 **5-30秒** 一次。不宜过于频繁以避免系统振荡
- **实现注意**: 需要在 `RequestsTimer` 中实现热更新，当前timeout值在构造时读取，需要支持运行时修改
- **调参范围建议**: [500ms, 30000ms]

### 14. ⭐ `system.totalordermulticast.batchtimeout` (已实现)
- **当前值**: `-1` (禁用，即不等待凑批)
- **用途**: 批处理超时。批处理等待的最长时间，超时后即使批没满也提交
- **类别**: 🟢 本地可调 — 每个节点独立决定何时提出批次（仅leader有效）
- **适合动态调参**: ✅ **已实现**
- **调参频率**: 高频，**1-5秒** 一次

### 15. ⭐ `system.totalordermulticast.maxbatchsize` (已实现)
- **当前值**: `1024`
- **用途**: 单次共识的最大批处理消息数
- **类别**: 🟡 半共识 — 仅leader节点使用此参数组装批次，但所有节点需要能处理收到的批次大小
- **适合动态调参**: ✅ **已实现**
- **调参频率**: 高频，**1-5秒** 一次

### 16. ⭐ `system.totalordermulticast.maxBatchSizeInBytes`
- **当前值**: `1000000` (约1MB)
- **用途**: 单次共识的最大批处理字节数
- **类别**: 🟡 半共识 — 与maxbatchsize类似，主要在leader组装批次时使用，但也影响其他节点的接收缓冲区
- **适合动态调参**: ✅ **适合** — 可以与maxbatchsize联动调整
  - 大消息场景下可能需要增大
  - 网络带宽受限时需要减小
- **调参频率**: 中频，**5-10秒** 一次
- **调参范围建议**: [100000, 10000000] (100KB - 10MB)

### 17. ⭐ `system.communication.useControlFlow`
- **当前值**: `1000`
- **用途**: 每个异步客户端的消息队列大小上限。超过此值的消息会被丢弃
- **类别**: 🟢 本地可调 — 完全本地的流控参数，不影响协议语义
- **适合动态调参**: ✅ **适合** — 可以根据负载动态调整
  - 高负载时增大以减少丢弃
  - 低负载时减小以节省内存
- **调参频率**: 低频，**30-60秒** 一次
- **调参范围建议**: [50, 5000]

### 18. `system.communication.maxRequestSize`
- **当前值**: `100000` (约100KB)
- **用途**: 单个客户端请求的最大字节数（含签名和元数据），超过则丢弃
- **类别**: 🟡 半共识 — 各节点可以设不同值，但如果不一致：
  - 宽松的节点可能接受并提出大请求
  - 严格的节点可能拒绝该请求，导致共识分歧
- **适合动态调参**: ⚠️ 有限度地适合。通常应保持一致
- **建议**: 静态配置，除非有特殊需求

### 19. `system.totalordermulticast.fairbatch`
- **当前值**: `false`
- **用途**: 是否在组装批次时随机遍历客户端（实现公平性）
- **类别**: 🟢 本地可调 — 仅影响leader如何选择下一批请求
- **适合动态调参**: ⚠️ 可以调但效果有限，通常不需要运行时改变
- **建议**: 静态配置

### 20. `system.totalordermulticast.nonces`
- **当前值**: `10`
- **用途**: 为非确定性操作生成的nonce数量
- **类别**: 🔴 需要共识 — 如果各节点nonce数不同，可能导致确定性复制出现分歧
- **适合动态调参**: ❌ 不适合
- **建议**: 静态配置

### 21. `system.totalordermulticast.verifyTimestamps`
- **当前值**: `false`
- **用途**: 是否验证leader生成的时间戳是递增的（需要时钟同步）
- **类别**: 🔴 需要共识 — 影响协议验证逻辑
- **适合动态调参**: ❌ 不适合
- **建议**: 静态配置

### 22. ⭐ `system.communication.inQueueSize`
- **当前值**: `500000`
- **用途**: 通信系统接收队列的容量
- **类别**: 🟢 本地可调 — 纯本地缓冲区大小
- **适合动态调参**: ✅ **适合** — 可以根据内存和负载动态调整
  - 高负载时增大以避免消息丢失
  - 但过大会消耗内存
- **调参频率**: 低频，**30-60秒** 一次
- **调参范围建议**: [10000, 1000000]
- **实现注意**: 需要确认底层队列是否支持运行时resize（可能需要用新队列替换旧队列）

### 23. ⭐ `system.communication.outQueueSize`
- **当前值**: `500000`
- **用途**: 每个副本的发送队列容量
- **类别**: 🟢 本地可调 — 纯本地缓冲区大小
- **适合动态调参**: ✅ **适合** — 同inQueueSize
- **调参频率**: 低频，**30-60秒** 一次
- **调参范围建议**: [10000, 1000000]
- **实现注意**: 同inQueueSize

### 24. `system.communication.useSignatures`
- **当前值**: `0` (不使用签名)
- **用途**: 0=不使用签名, 1=使用签名, 2=仅验证不创建（基准测试用）
- **类别**: 🔴 需要共识 — 所有节点必须一致，否则签名验证会失败
- **适合动态调参**: ❌ 不适合
- **建议**: 静态配置

### 25. `system.shutdownhook`
- **当前值**: `true`
- **用途**: 关闭时是否打印副本信息
- **类别**: 🟢 本地可调 — 纯本地行为
- **适合动态调参**: ❌ 不需要动态调
- **建议**: 静态配置

### 26. `system.samebatchsize`
- **当前值**: `false`
- **用途**: 强制所有副本向应用层交付相同数量的请求（注意：不是排序协议中的批次）
- **类别**: 🔴 需要共识 — 涉及交付语义的一致性
- **适合动态调参**: ❌ 不适合
- **建议**: 静态配置

### 27. ⭐ `system.numrepliers`
- **当前值**: `16`
- **用途**: 向客户端发送回复的线程池大小（0=无线程池，由delivery线程串行发送）
- **类别**: 🟢 本地可调 — 纯本地线程池配置
- **适合动态调参**: ✅ **适合** — 可以根据客户端数量和负载动态调整
  - 客户端多时增大线程池
  - 负载低时减小以节省资源
- **调参频率**: 低频，**30-120秒** 一次
- **调参范围建议**: [0, 64]
- **实现注意**: 需要实现线程池的动态resize或重建（`ReplyManager`需要支持热更新）

## 三、状态传输配置（State Transfer Configurations）

### 28. `system.totalordermulticast.state_transfer`
- **当前值**: `true`
- **用途**: 是否启用状态传输协议（允许落后的节点追赶）
- **类别**: 🔴 需要共识 — 所有节点必须一致，否则有的节点会尝试状态传输而有的不会
- **适合动态调参**: ❌ 不适合
- **建议**: 静态配置

### 29. ⭐ `system.totalordermulticast.highMark`
- **当前值**: `10000`
- **用途**: 最大允许的"超前"消息数量。超过此值的提前到达的共识消息会被丢弃
- **类别**: 🟡 半共识 — 理论上各节点可以不同，但如果差异太大：
  - 值太小的节点会丢弃合法的超前消息，导致其频繁触发状态传输
  - 值太大会消耗大量内存
- **适合动态调参**: ✅ **适合** — 可以根据系统负载和网络延迟调整
  - 高延迟/高吞吐场景下增大以容纳更多超前消息
  - 低负载时减小以节省内存
- **调参频率**: 低频，**60-300秒** 一次
- **调参范围建议**: [1000, 50000]

### 30. `system.totalordermulticast.revival_highMark`
- **当前值**: `10`
- **用途**: 节点在EID=0时（刚启动/恢复）允许的超前消息数上限，超过后触发状态传输
- **类别**: 🟢 本地可调 — 仅影响本节点的恢复行为
- **适合动态调参**: ❌ 通常不需要。仅在节点启动/恢复时有意义
- **建议**: 静态配置

### 31. ⭐ `system.totalordermulticast.timeout_highMark`
- **当前值**: `200`
- **用途**: 请求超时后，需要多少个超前消息才触发状态传输。即当前节点超时且发现有 ≥ timeout_highMark 个超前消息时，认为自己严重落后，触发状态传输
- **类别**: 🟡 半共识 — 各节点可以不同，但差异过大会导致状态传输触发时机不一致
- **适合动态调参**: ✅ **适合** — 与timeout参数联动
  - 网络频繁抖动时增大，避免频繁触发不必要的状态传输
  - 节点性能差距大时可以减小，让落后节点更快赶上
- **调参频率**: 低频，**60-300秒** 一次
- **调参范围建议**: [10, 1000]

## 四、日志和检查点配置（Log and Checkpoint Configurations）

### 32. `system.totalordermulticast.log`
- **当前值**: `true`
- **用途**: 是否启用共识决策日志
- **类别**: 🟢 本地可调 — 影响本节点能否支持状态传输中的日志回放
- **适合动态调参**: ⚠️ 理论上可以，但运行时关闭日志可能导致无法完成状态传输
- **建议**: 静态配置

### 33. `system.totalordermulticast.log_parallel`
- **当前值**: `false`
- **用途**: 是否并行写日志
- **类别**: 🟢 本地可调
- **适合动态调参**: ⚠️ 可以但效果有限
- **建议**: 静态配置

### 34. `system.totalordermulticast.log_to_disk`
- **当前值**: `false`
- **用途**: 是否将日志写入磁盘
- **类别**: 🟢 本地可调
- **适合动态调参**: ❌ 运行时切换会导致数据不一致
- **建议**: 静态配置

### 35. `system.totalordermulticast.sync_log`
- **当前值**: `false`
- **用途**: 是否同步写日志（fsync）
- **类别**: 🟢 本地可调
- **适合动态调参**: ⚠️ 可以但对性能影响较大
- **建议**: 静态配置

### 36. ⭐ `system.totalordermulticast.checkpoint_period`
- **当前值**: `1024`
- **用途**: 每隔多少个共识实例做一次检查点（checkpoint），用于状态传输。影响：
  - 值小 → 检查点频繁，状态传输更快，但overhead大
  - 值大 → 检查点稀疏，节省CPU，但落后节点恢复慢
- **类别**: 🔴 需要共识 — 检查点周期不一致会导致节点间状态快照号不对齐，影响状态传输协议
- **适合动态调参**: ✅ **适合但需谨慎** — 需要所有节点同步更改
  - 高吞吐时可增大检查点周期以减少overhead
  - 频繁有新节点加入时减小以加速恢复
- **调参频率**: 极低频，**5-15分钟** 一次
- **调参范围建议**: [128, 8192]
- **实现要求**: **必须通过共识协议同步变更**

### 37. ⭐ `system.totalordermulticast.global_checkpoint_period`
- **当前值**: `120000` (ms，约2分钟)
- **用途**: 基于时间的全局检查点周期
- **类别**: 🔴 需要共识 — 同checkpoint_period，所有节点必须一致
- **适合动态调参**: ✅ **适合但需谨慎**
- **调参频率**: 极低频，**5-15分钟** 一次
- **调参范围建议**: [30000, 600000] (30s - 10min)

### 38. `system.totalordermulticast.checkpoint_to_disk`
- **当前值**: `false`
- **用途**: 是否将检查点写入磁盘
- **类别**: 🟢 本地可调
- **适合动态调参**: ❌ 运行时切换风险高
- **建议**: 静态配置

### 39. `system.totalordermulticast.sync_ckp`
- **当前值**: `false`
- **用途**: 是否同步写检查点
- **类别**: 🟢 本地可调
- **适合动态调参**: ❌ 同上
- **建议**: 静态配置

## 五、重配置相关（Reconfiguration Configurations）

### 40. `system.initial.view`
- **当前值**: `0,1,2,3`
- **用途**: 初始视图中的副本ID列表
- **类别**: 🔴 需要共识 — 定义初始群组成员
- **适合动态调参**: ❌ 不适合。使用BFT-SMaRt自带的reconfiguration机制
- **建议**: 静态配置

### 41. `system.ttp.id`
- **当前值**: `7002`
- **用途**: 可信第三方（TTP）的进程ID
- **类别**: 🔴 需要共识 — 所有节点必须信任同一个TTP
- **适合动态调参**: ❌ 不适合
- **建议**: 静态配置

### 42. `system.bft`
- **当前值**: `true`

## 八、优化配置

### 47. `system.optimizations.readonly_requests`
- **当前值**: `false`
- **用途**: 是否启用无序读请求优化。启用后：

  - 服务端维护reply store用于状态传输
- **类别**: 🔴 需要共识 — 影响协议语义、quorum计算和客户端行为
- **适合动态调参**: ❌ 不适合。涉及客户端和服务端协议的根本变更
- **建议**: 静态配置

## 实现建议

### 对于本地可调参数
直接复用现有的 `setDynamicConsensusConfig()` 模式：
1. 在 `TOMConfiguration` 中添加对应的 setter（使用 `volatile` 确保线程安全）
2. 在 `ServiceReplica` 中暴露设置方法
3. 在 `RLAgentConnector` 中扩展 gRPC 协议传输新参数

### 对于半共识参数（如 timeout）
建议采用"最终一致"策略：
1. 各节点独立调参，但调参范围限制在合理区间内
2. 通过 gRPC 将调参结果同步到所有节点（通过 Agent 中心化协调）
3. 设置安全上下限防止极端值

### 对于需要共识的参数（如 checkpoint_period）
需要扩展 BFT-SMaRt 的 reconfiguration 协议：
1. 定义新的 `ReconfigureRequest` 类型
2. 通过共识协议将参数变更作为一个特殊的系统交易提交
3. 在共识达成后，所有节点在同一个共识序列号上同步切换参数值
